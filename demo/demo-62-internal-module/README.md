InternalModule demo
===================

Add a code generator to the stock build as a plugin - a build module kept in its
own project and compiled from local source - named in one line of
`jenesis.plugins.properties` and configured by a properties file of its own. The
plugin generates a `Greeting` class from a configured text before the regular
compile, jar and test flow runs, and it leans on an external dependency
(`org.json`) to do so.

Run it
------

From this directory:

    java build/jenesis/Execute.java

which builds the project and then launches the built module, printing the
greeting the plugin generated:

    Hello from a source generated by an internal build module, using the org.json dependency!

Built without the plugin, `sample.Greeting` would not exist and the project would
not compile. A second plugin observes the tests: it records which classes their JVM
loads and reports those of the package `sample`, in
`target/.../observed/observations/loaded/loaded/output/reports/loaded/loaded.txt`:

    sample.Sample

A third plugin is the framework the tests run on: it runs them on the JUnit
Platform, as the built-in framework would, and hands them the system property
`demo.framework`, which one of the tests asserts.

Layout
------

    demo/demo-62-internal-module
    |-- build/jenesis                 symlink to ../../../sources/build/jenesis
    |-- jenesis.plugins.properties    greeting+binary/generated=./plugin
    |                                 loaded+observe=./observer
    |                                 platform+test=./framework
    |-- build.jenesis/
    |   |-- plugin-loaded.properties     package=sample
    |   `-- plugin-platform.properties   empty: the plugin takes no values
    |-- framework/
    |   |-- .jenesis.skip
    |   |-- module-info.java     module demo.framework { requires build.jenesis;
    |   |                                provides build.jenesis.TestFrameworkFactory
    |   |                                with demo.framework.PlatformFactory; }
    |   `-- demo/framework/PlatformFactory.java
    |-- plugin/
    |   |-- .jenesis.skip       marks plugin/ as its own build root, so the
    |   |                        project's module discovery skips it
    |   |-- module-info.java     module demo.plugin { requires build.jenesis;
    |   |                                requires org.json;
    |   |                                provides build.jenesis.BuildModuleFactory
    |   |                                with demo.plugin.GreetingFactory; }
    |   |-- demo/plugin/GreetingFactory.java
    |   `-- demo/plugin/GreetingModule.java
    |-- observer/
    |   |-- .jenesis.skip
    |   |-- module-info.java     module demo.observer { requires build.jenesis;
    |   |                                provides build.jenesis.ObservabilityFactory
    |   |                                with demo.observer.LoadedFactory; }
    |   `-- demo/observer/LoadedFactory.java
    |-- sources/
    |   |-- META-INF/build.jenesis/
    |   |   `-- plugin-greeting.properties   greeting=Hello from a source generated by ...
    |   |-- module-info.java     module demo.internal { exports sample; }
    |   `-- sample/Sample.java    prints Greeting.TEXT
    `-- tests/
        |-- module-info.java     the @jenesis.test module of demo.internal
        `-- sampletest/GreetingTest.java

The project under `sources/` and `tests/` is an ordinary modular project. The build
modules under `plugin/`, `observer/` and `framework/` are separate modular projects; their
`.jenesis.skip` marker keeps the host project's module discovery from mistaking
them for project modules.

Naming the plugin
-----------------

`jenesis.plugins.properties` sits beside `jenesis.properties` and names one plugin
per line:

    greeting+binary/generated=./plugin

The key is `<name>+<hook point>`: the plugin's name (`greeting`), and the place in
the stock build it joins - here `binary/generated`, where generated sources are
compiled with the project's own. The value is where the
plugin comes from: a value starting with `./` is a folder compiled from source,
anything else a module name resolved from a repository. Either may end in
`@<provider>` to select the provider annotated `@BuildModuleName("<provider>")`
when the plugin module provides several. The hook points of a module are `check`, `format`,
`compliance`, `binary`, `binary/generated`, `binary/compiled`, `binary/validate`,
`artifact`, `observed`, `observe`, `test`, `documentation`, `documentation/generate` and `package`; a key
without `+<hook point>` adds the plugin to the module build itself. A plugin reads what
the module it joins reads, and adds to it: it never replaces a stock step.

Configuring the plugin
----------------------

A plugin runs only in a module where `plugin-<name>.properties` is found, looked
up like any other configuration file - in the module's own `META-INF/build.jenesis/`,
then in `build.jenesis/`, with profiles first. The generator belongs to the main
module alone, so its file sits in `sources/META-INF/build.jenesis/`, where the test
module does not see it:

    greeting=Hello from a source generated by an internal build module, using the org.json dependency!

The plugin provides a `BuildModuleFactory`, and the build hands the file's values
to its `create` method as a `SequencedMap<String, String>`, in the file's order,
beside the build's settings, the build's process permits, the dependency group
named after the plugin - `greeting` here - in which to resolve a tool, and the build's
repositories and resolvers. A value `@<key>`, or `@<key>/<default>`, is the setting
`jenesis.variable.<key>`, read before the plugin sees it, and `@@` writes a literal `@`. The factory returns the module that is wired:

    public BuildExecutorModule create(Environment environment,
                                      SequencedMap<String, String> properties,
                                      Permits permits,
                                      String group,
                                      Map<String, Repository> repositories,
                                      Map<String, Resolver> resolvers) {
        return new GreetingModule(properties);
    }

The plugin's `greeting` step writes `sources/sample/Greeting.java` into its output,
quoting the text with `org.json`, and `javac` compiles it with `Sample.java`. What
a plugin generates is part of the module's sources from then on: `javadoc`
documents `Greeting`, and the sources jar that `-Djenesis.project.sources=true`
stages carries `sample/Greeting.java` beside `sample/Sample.java`.

The plugin's dependencies - `build.jenesis` and `org.json` - resolve from the
default Jenesis repository, with the local export (`~/.jenesis`) searched first,
and are pinned in `sources/module-info.java` under the dependency group named
after the plugin:

    @jenesis.pin greeting/module/build.jenesis 0.13.1 SHA-256/...
    @jenesis.pin greeting/module/org.json 20260522 SHA-256/...

Observing the tests
-------------------

A plugin of the hook point `observe` attaches to the JVM the tests run in and
reports over what it recorded, as JaCoCo does. It provides an
`ObservabilityFactory` rather than a `BuildModuleFactory`, handed the same, and
returns an `Observation`: the `ObservabilityEngine` whose JVM options join the
test run, and the module that reads what the run left behind.

    return new Observation(new ClassLoading(group),
            (executor, inherited) -> executor.addStep("loaded", new Loaded(prefix), inherited.sequencedKeySet()));

The engine here adds `-Xlog:class+load` and writes its log into the test step's
output; the `loaded` step finds that log among its arguments and keeps the classes
of the package that `plugin-loaded.properties` names. The engine is part of what
decides whether the tests run again, so a changed value runs them anew, and an
unchanged build runs neither the tests nor the report. Only the module that runs
tests is observed: the main module has none, and `plugin-loaded.properties` in
`build.jenesis/` changes nothing there.

Running the tests on a framework of your own
--------------------------------------------

A plugin of the hook point `test` provides a `TestFrameworkFactory`, handed the
same, and returns a `TestFramework`: the runner the tests' JVM starts, the
arguments it takes, and the modules that mark a test module as its own. The
frameworks a project declares are consulted first, in the order
`jenesis.plugins.properties` names them, and the built-in JUnit Platform, JUnit 4
and TestNG after them, so the first one that a module of the tests marks runs
them. A `framework=<name>` line in `test.properties` may name a declared framework
by its plugin name as well as a built-in one.

This demo's `Platform` delegates to the built-in `JUnitPlatform` and adds the
system property:

    @Override
    public Map<String, String> systemProperties() {
        Map<String, String> properties = new LinkedHashMap<>(platform.systemProperties());
        properties.put("demo.framework", name);
        return properties;
    }

The framework is part of what decides whether the tests run again, as the
built-in ones are, so it holds its settings as serialisable fields.

Isolating the build module's Jenesis
------------------------------------

A build module brings its own `build.jenesis` (here the one pinned in
`sources/module-info.java`), which is generally a *different* copy from the
Jenesis running the build. To let the two coexist, `InternalModule` loads the
module into its **own `ModuleLayer` with its own class loader**, so the module's
`build.jenesis` never clashes with the host's on a single class path. A
class-loader bridge (`JenesisClassLoaderBridge`) then translates across the
boundary: the host invokes the module's `BuildExecutorModule.accept` and
`BuildStep` methods by method handle, and the module's calls back onto the
`BuildExecutor` it is handed run through a proxy that dispatches to the host's
executor.

This isolation rests on a **module layer**: the module is resolved into a
`ModuleLayer` and its `BuildModuleFactory` is discovered there as a service provider. A
service provider is found through its module's `provides` declaration, so the
**build module itself must be a named (explicit) module** - this plugin's
`module-info.java` is what makes it loadable as a service at all. Its
*dependencies*, by contrast, are not restricted to named modules: a module layer
admits automatic modules too, so what a build module may depend on comes down to
how those dependencies are resolved. This demo resolves them by Java module name
from the Jenesis module repository (and `org.json` here is itself a named module),
but `InternalModule` takes arbitrary resolvers - wire a Maven resolver and the
closure is fetched by coordinate, which is how an automatic-module or otherwise
non-modular dependency is brought in and loaded into the layer. (The pure MODULAR
*layout* in `../demo-23-module-layout` is the stricter case: it resolves only by
module name and so rejects automatic modules outright.)

Because the two `build.jenesis` copies are isolated rather than merged, a build
module can pin a different Jenesis version than the host without conflict - as
long as the API surface it uses lines up. If a module built against a *newer*
Jenesis calls a `BuildExecutor` method this (older) Jenesis does not provide, the
bridge cannot map it and fails with an `UnsupportedOperationException` that names
the method and tells you to upgrade Jenesis, rather than a confusing linkage
error.
