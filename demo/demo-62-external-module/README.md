ExternalModule demo
===================

Add the code generator of the `internal-module` demo to the stock build as a
plugin that ships as a published module, resolved from a repository by its module
name rather than compiled from local source. The plugin, its configuration and
the outcome are the same; only the value in `jenesis.plugins.properties` names a
module instead of a folder.

Run it
------

From this directory:

    java build/Demo.java

which publishes the plugin into a local module repository, builds the project and
launches the built module, printing the greeting the plugin generated:

    Hello from a source generated by an external build module, using the org.json dependency!

Layout
------

    demo/demo-62-external-module
    |-- build/jenesis                 symlink to ../../../sources/build/jenesis
    |-- build/Demo.java               publishes the plugin, then builds and runs
    |-- jenesis.plugins.properties    greeting+binary/generated=demo.plugin@greeting
    |-- build.jenesis/
    |   `-- plugin-greeting.properties   greeting=Hello from a source generated by ...
    |-- plugin/                       the build module (as in internal-module)
    |   |-- .jenesis.skip
    |   |-- module-info.java          module demo.plugin { ... with demo.plugin.GreetingFactory; }
    |   |-- demo/plugin/GreetingFactory.java
    |   `-- demo/plugin/GreetingModule.java
    `-- sources/                      the project being built (as in internal-module)

Naming the plugin by module
---------------------------

    greeting+binary/generated=demo.plugin@greeting

A value that does not start with `./` is a module name. The build resolves it as
`module/demo.plugin` through the Jenesis module repository - whatever the
project's layout - with the local export searched first, loads the module's
`BuildModuleFactory` and runs the module it creates at the `binary/generated` hook point, as the
`internal-module` demo does with the one it compiles.

The `@greeting` after the module name selects the provider to run. This demo's
copy of the plugin annotates `GreetingFactory` with `@BuildModuleName("greeting")`,
which a module that provides several factories uses to tell them apart; an
annotated factory runs only where it is named, so the line must say `@greeting`.
Without an `@`, as in `internal-module`, the module must provide exactly one
unannotated factory.

A real plugin is published once and resolved by everyone who names it. To stand
in for that, `build/Demo.java` first builds `plugin/` as a project of its own and
runs its `export` selector, with `jenesis.module.local` pointing at
`target/local`, and then builds and runs this project with the same setting, so
the module repository finds `demo.plugin` there:

    Project.ofEnvironment(environment, Path.of("plugin")).target(Path.of("target", "plugin")).version("1.0.0").build("export");
    System.exit(new Execution(Project.ofEnvironment(environment, Path.of("."))).execute(args));

A plugin found in the local export is pinned and checked like one from a
repository, which is why the plugin is exported as version `1.0.0`: `pin` records
it in `sources/module-info.java` with the dependencies it brings - `build.jenesis`
and `org.json` - under the group named after the plugin, `plugin-greeting`, so the
build runs under `-Djenesis.dependency.pin=strict`. Change the plugin and its
checksum changes with it; `-Djenesis.dependency.pin=versions` with `pin` records
what the export now holds.

Isolating the build module's Jenesis
------------------------------------

Just as in `../demo-61-internal-module`, the resolved build module is loaded into
its **own `ModuleLayer` with its own class loader** carrying its own
`build.jenesis`, bridged to the host across class loaders so the two Jenesis
copies never clash and the module may pin a different version. The build module
itself must be a named (explicit) module, since it is discovered in that layer as
the provider of a `BuildModuleFactory`; its *dependencies* are not so
restricted - a module layer admits automatic modules too, so dependencies
resolved by Maven coordinate (rather than by module name, as this demo does) can
include automatic or otherwise non-modular jars. A module built against a *newer*
Jenesis that calls a `BuildExecutor` method this version lacks fails with an
`UnsupportedOperationException` advising you to upgrade Jenesis. See that demo's
"Isolating the build module's Jenesis" section for the full explanation.
